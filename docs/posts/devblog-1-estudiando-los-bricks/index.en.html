2. Technology and project definition

The only thing I've touched to hack together the odd thing is Unity, so the engine is an easy pick.
For the multiplayer part (if I ever get to it), Unity's official library is dead, so I'll go with Mirror.
It's an open source library maintained by competent people.

As for the project definition, the more tightly I scope it, the higher the chance I'll finish it.
The idea is to be able to build in first person like in minecraft, but with bricks. No enemies, no procedural world.
- FPV (First Person View) controller
- Inventory system
- Building system
- Multiplayer (if I manage to finish everything above)

Now comes the nasty part, positioning new blocks.

In Minecraft placing a new block is really easy. The whole world is one big three-dimensional matrix and all objects have the same shape (cube), so all you have to do is check whether that space in the matrix is free.


But with bricks?... What a pain. We could make a matrix using plates as the unit, but we'd have to calculate the spaces taken up by bricks like:

Unity has a component called "Collider" that lets you work with physics. That is, make an object take up space or act as a hitbox, detecting when another object is inside it (trigger).


In this example, the cubes with green edges are the colliders.

We'll show a preview of where the new block will appear and give this preview a collider in trigger mode.

For those who don't know, raycasting is this:

4. The damn inventory system

As usual I underestimated how complex it would be. I thought it'd be 10 lines, give or take, and off we go, but no. Turns out there's more to it than meets the eye.

I always need to start with the visual part, not because I'm good at it, but because unlike banging out code, even a little work shows a visible change.
Making use of my GREAT creativity, I've come up with the following design:


Now it's back to the code.

We'll start with the data model. What are we going to have to store? The item id, the amount and its state.


Done! Right? Well no.. We forgot the slot it's in within the inventory. And that little piece of crap is what adds the complication, because eeevery time an item is added to the inventory, we'll have to find it an available slot (as long as we don't already have it). And whenever possible, the fast access slots have to be prioritized, the ones on the bottom bar basically.


Fine, let's add the damn slot.

What will our inventory have to do?/What do we need to keep in mind?
- Add and remove items
- When they're added, always prioritize filling the bottom bar
- When items are added or removed the UI has to update
- In the inventory panel you have to be able to move items between slots via drag & drop.
- In the inventory panel, if an item is dragged outside the window, it has to be discarded.
- In the bottom bar there always has to be a selected slot
- You have to be able to change the selected slot of the bottom bar
- When in the inventory panel, the player's camera has to be frozen
- All bricks need a preview icon

Dang, this is longer than I thought.

The add item function alone already beats the 10 lines, give or take, that I expected to write xD


As you can see, when adding an item, the first thing I do is iterate over the whole inventory, to do 2 things:
Check whether I already have that item, so I only need to increase the amount, and note down the occupied slots.

If I don't find the item, I'll at least know which slots I can't fill. After that, since I know for sure a new slot has to be taken, I check whether the inventory is full. If it isn't, I keep going, and iterate over the remaining free slots to see if any of them is in the bottom bar (the inventory has 36 slots, so I check whether the free slot is > 27).
If that's not possible, I just grab the first available one and screw it. Oh right, and I update the UI.

Next up we do the part of moving items between slots. For that we'll use Unity's drag&drop system, via IBeginDragHandler, IDragHandler, IEndDragHandler.


It might look like I've moved the icon somewhere else but I'm not actually doing that.
Instead of dynamically generating the occupied slots, I have them all already generated statically, whether they're full or empty.
After dragging, when the icon is dropped, what I do is check which slot you were moving and where you dropped it. I put the slot you moved back in its place and swap the contents of the 2 slots via code (if they have anything).


On to having a selected slot. This part is a bit problematic for me because we're used to using the mouse wheel to move between our weapons/inventory. But I've assigned the brick rotating function to the wheel. It felt natural to me and I don't see how I could tell when you want to rotate a cube from when you want to change slot so that both can use the wheel.
The only way would be if the process of adding a brick were:
1. You aim at the stud and left click.
2. This makes the preview appear, and now you can use the wheel to rotate it.
3. You left click to confirm the build.


It feels cumbersome/slower to me. And since you also don't have the preview in the first step, you might not realize that unlike minecraft, you can aim at exactly which stud you want to put it on.
Although on the other hand..
1. This would let me use the wheel to move through the inventory, since there would only be one moment when the building system uses it and I'd know whether you're in that step or not.
2. Another win would be that you could walk around the map with a brick selected in the inventory without the preview showing up wherever you look.
3. I wouldn't have to be raycasting every frame, only once the player left clicks, because I'd know they want to build. [Although now that I think about it, I can avoid this right now too, by checking whether the selected item is a brick].


MMMMMMMmmm. There might be more pros than cons after all.


I'll have to chew on it.
