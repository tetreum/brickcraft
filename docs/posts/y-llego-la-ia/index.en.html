Internal event system

Until now Brickcraft only had 1 AssemblyFile. In other words, aaaall the code was lumped into a single file.
Which meant that eeeeeeeeeeevery time, for example, the UI was edited, the game mechanics' code was recompiled. No matter what you touched, everything had to be recompiled.

The way to avoid this is splitting the code into multiple AssemblyFiles: the UI in one place, the AI in another, the mechanics in another, etc. But of course, these sections still need to talk to each other.

The solution is to create an event system, so one side emits and the other listens.
Again, this isn't something I fancied doing by hand, so the AI took on the refactor.

Multiplayer

Since I'd focused entirely on the building mechanics, the game was singleplayer and not much else.
When you want to make a multiplayer game, the process is a pain, even using third-party libraries.
The reason is that in this kind of game you want to stop the player from cheating, which means the server has to validate each and every sensitive action.

If, for example, you want to place a block, where before we'd have something as simple as:

void addBlock(Vector3 position, string type) {
 if (!IsValidPlacement(position)) return;
   return;
 }
 Instantiate("prefabs/type", position);
}

To make it secure it would end up, at MINIMUM, like this:

public void RequestAddBlock(Vector3 position, string type)
    {
        if (IsServer)
        {
            AddBlockServerInternal(position, type);
        }
        else
        {
            AddBlockServerRpc(position, type);
        }
    }

    [ServerRpc(RequireOwnership = false)]
    private void AddBlockServerRpc(Vector3 position, string type)
    {
        if (!IsValidPlacement(position)) return;

        AddBlockServerInternal(position, type);
    }

    private void AddBlockServerInternal(Vector3 position, string type)
    {
        GameObject prefabToSpawn = GetPrefabForType(type);

        GameObject blockInstance = Instantiate(prefabToSpawn, position, Quaternion.identity);

        NetworkObject netObj = blockInstance.GetComponent<NetworkObject>();
        netObj.Spawn();
    }

A constant ping-pong between client and server, what's known as authoritative multiplayer.
Thanks to AI, migrating the existing code to this wall of text was automatic, and for that I relied on the Mirror library (because it's free and open source).
That said, the auth part is a bit flimsy when it comes to how easy it is to impersonate other users. The only good way I see to avoid that would be publishing the game on Steam so I could use its auth. That's left for another iteration. For the same reason I haven't enabled creating dedicated servers. It's not worth it for now.

Importing and exporting models

The need is clear: you have to be able to build anything in-game and then export it so the game itself can use it.
To do that there's an item that, when you right click a block, goes looking for every block connected to it to work out the model's bounding box, which is just a box representing its limits. Since there's room to screw it up (imagine you've changed the floor you built on but don't want it to be part of the model), there's an option to edit the bounding box by hand before generating the model.

While we're at it, we optimize the generated model by doing things like removing the studs of pieces that have another piece on top. You can't see them, so we can spare them.

Making the exporter also unlocked the main reason I started this game: being able to build models intuitively, aka Minecraft-style, and then buy the physical pieces they're made of and build it in real life.
At first I was looking at and implementing the format websites like BrickLink use to import a list of pieces you want to buy. (https://www.bricklink.com/help.asp?helpID=2567)

Added mod support

Mods usually need 3 things: running code, creating UIs and adding models.
I'm not one bit happy about third-party code running on my PC, so it has to be something I know will be locked down to the bare minimum. So the choice is obvious: Lua.
Lua is an embeddable language. Unlike, say, C#, the functions a Lua script can reach are limited to exactly the ones the programmer enables. A Lua script will have a hard time downloading and running an .exe from the internet. And on top of that it doesn't even weigh 1MB.

Adding mods brings a whole bunch of changes to the systems we already had: the server must not only validate the client's version, but also that it has the right mods, in the expected version.
The most typical UI components (button, alert, panel...) also have to be created, so Lua can use presets.
And little by little, wire up every system we want them to reach: like reading the blocks at certain coordinates, spawning creatures there, or doing something at a certain time of day.

Although of course, for many of those functions we'd first need NPCs and a day/night cycle.

Day cycle

To add a day cycle you have to think about how much real-life time each in-game day will last, and track it on the server to know which "day number" we're on in-game.
Then it's a matter of showing it visually by rotating the light that acts as the Sun at a speed that completes the cycle in that time, and adding the moon.

We're in a world of blocks, so if you zoom in on the moon you'll see it's made of blocks too :p

But of course, not all of us like playing at night. Time has to be skippable.
This is where the system that lets us create new items out of multiple pieces comes into play. Thanks to it we have a bed to script so that clicking it makes the character sleep and the night pass faster.

And of course, commands have been added to switch to whatever time of day you want if you're an admin.

Beds have also been made the respawn point in case you kick the bucket.

NPCs

Adding AI to a game is a slog; doing it in multiplayer is twice that.
The first thing to consider is which navigation system they'll use. Unity has navmesh, but like everything Unity makes, it has its problems.

Imagine you want the user to be attacked by a group of enemies. Unity doesn't consider that possibility, which means the enemies don't see each other, so they all pick the same route (the shortest). Forming a queue that makes no sense at all, because normally each one would try to keep line of sight with its target (to be able to shoot it, for example).

The usual hack is adding a component called NavMeshObstacle to each enemy, which, as you can see in one of the previous images, removes the space it takes up from the navigation system (that's the blue area). That way the space is marked as taken and the next enemy doesn't even consider walking through it.
But of course, things with a NavMeshObstacle CAN'T move. So what people do is enable the component, recalculate the route and disable it, constantly.
Extraordinarily gross.

Another detail is that Unity's pathfinding is single-threaded; it has to run on the main thread.

Knowing the official solution is utter crap, I chose to create one that uses the grid generated when building the world out of blocks. After all, in the worst case it'll be just as bad as the official one.

It wasn't the only change made to reach those frames. Every chunk generated its collider even when far from the player. Not giving every chunk a collider is what let the NPCs walk on water.

Making key remapping easier

In Unity, if you want to know whether the player is pressing a certain key, you just have to do:

if (Input.GetKeyDown(KeyCode.Space)) {
  // pressing the Space bar
}

Simple and convenient, but with one problem. The key is hardcoded. The player can't change it to another one.
The hack used to get around that was putting a class in between that kept the relation between an action and a key, so the code ended up as:

if (Input.GetKeyDown(GameInput.keyFor("Jump"))) {
  // pressing the Space bar
}

Well, Unity's InputSystem does exactly that, but officially and with more improvements, including letting you fake the keys being pressed. And why would anyone want to fake key presses? To be able to add tests.

Stabilizing the game?

Usually validating a flow in an application is relatively simple.
Want to check that sign-up works automatically? You just have to follow a few steps:

  1. Go to example.com/signup
  2. Fill in the email and password fields
  3. Press the submit button
  4. Check that the new record is in the database.

With video games, however, the plot thickens. We're now in a 3D environment, and if on top of that it's a sandbox, there are mechanics that can play tricks on you and make a check fail intermittently.

  • What if, while you're testing placing a block on top of another, a creature shows up from behind, smacks the player and moves them before the block is placed?
  • What if you're testing hitting a tree but the game has a randomness mechanic that makes it miss?

You have to try to make everything as deterministic as possible. Everything random has to be seeded. Every mechanic that could interfere has to be controlled.
Even so, it's usually the combination of several mechanics that causes a bug.
For example: I made right clicking with nothing in your hand zoom in. Now every time you drank a potion the system zoomed in. Because at first the potion was there, but then it wasn't.

I don't know the perfect way to fix this, but I've tried to give the game a minimum of checks to avoid messes in the most basic mechanics.
Ideally they'd run on every PR, but I have to check whether that's doable, because I know Unity likes to complain if its runtime is run the wrong way.
We'll see; for now we have tests even for fluids.
