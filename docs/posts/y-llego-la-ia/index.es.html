Sistema de eventos interno

Hasta ahora Brickcraft sólo tenía 1 AssemblyFile. Dicho de otra manera, toooodo el código se juntaba en un único fichero.
Lo que se traduce en que caaaaaaaaaaada vez que por ejemplo se editaba la UI, el código de las mecánicas del juego se recompilaba. Daba igual lo que tocases que había que recompilar todo.

La forma de evitar que esto ocurra es dividiendo el código en múltiples AssemblyFiles: La UI por un sitio, la IA por otro, las mecánicas por otro, etc.. Pero claro, estas secciones siguen necesitando hablar entre ellas.

La solución es crear un sistema de eventos, de manera que un lado emita y el otro esté a la escucha.
De nuevo no es algo que me interesara hacer a manija, así que la IA se ha comido el refactor.

Multiplayer

Dado que me había centrado de lleno en las mecánicas de construcción, el juego era singleplayer y poco más.
Cuando quieres hacer un juego multijugador el proceso, aún usando librerías de terceros, es un coñazo.
El motivo es que en este tipo de juegos, quieres evitar que el jugador haga trampas y ello significa que el servidor debe validar todas y cada una de las acciones sensibles.

Si por ejemplo quieres poner un bloque, donde antes tendríamos algo tan simple como:

void addBlock(Vector3 position, string type) {
 if (!IsValidPlacement(position)) return;
   return;
 }
 Instantiate("prefabs/type", position);
}

Para hacerlo seguro quedaría MÍNIMO en esto:

public void RequestAddBlock(Vector3 position, string type)
    {
        if (IsServer)
        {
            AddBlockServerInternal(position, type);
        }
        else
        {
            AddBlockServerRpc(position, type);
        }
    }

    [ServerRpc(RequireOwnership = false)]
    private void AddBlockServerRpc(Vector3 position, string type)
    {
        if (!IsValidPlacement(position)) return;

        AddBlockServerInternal(position, type);
    }

    private void AddBlockServerInternal(Vector3 position, string type)
    {
        GameObject prefabToSpawn = GetPrefabForType(type);

        GameObject blockInstance = Instantiate(prefabToSpawn, position, Quaternion.identity);

        NetworkObject netObj = blockInstance.GetComponent<NetworkObject>();
        netObj.Spawn();
    }

Un ping pong constante entre cliente y servidor, lo que se conoce como authoritative multiplayer.
Gracias a la IA, la migración del código existente a esta parrafada ha sido automática y para ello me he valido de la librería Mirror (porque es gratis y opensource).
Dicho esto la parte de auth es un poco chuchurría en cuanto a la facilidad de impersonar a otros usuarios. La única forma buena que veo para evitar esto, sería publicar el juego en Steam para poder usar su auth. Cosa que se queda para otra iteración. Por el mismo motivo no he habilitado la creación de servidores dedicados. Por ahora no vale la pena.

Importación y exportación de modelos

La necesidad está clara: se tiene que poder montar lo que sea ingame y luego exportarlo de manera que el propio juego pueda usarlo.
Para ello se ha montado un objeto que al hacer clic derecho sobre un bloque, se pone a buscar todos los bloques que conecten con este a fin de determinar la bounding box del modelo, que no es más que una caja que representa los límites de este. Como hay margen de cagarla (imagina que has cambiado el suelo sobre el que has construído pero no quieres que forme parte del modelo), se ha incluído la opción de editar la bounding box manualmente antes de generar el modelo.

Ya que estamos, el optimizaremos el modelo generado a base de hacer cosas como eliminar los studs que aquellas piezas que tengan otra pieza encima. Pues no se ven y por tanto nos las podemos ahorrar.

Añadido soporte para mods

Los mods suelen requerir de 3 cosas: poder ejecutar código, poder crear UIs y poder meter modelos.
No me hace ni puta gracia que se ejecute código de terceros en mi PC, así que tiene que ser algo que sepa que estará capado a la mínima expresión. La elección por tanto es obvia: Lua.
Lua es un lenguaje embebible. A diferencia de por ejemplo C#, las funciones a las que un script de lua pueda acceder están exactamente limitadas a las que el programador habilite. Un script lua difícilmente podrá descargarse y ejecutar un .exe de internet. Y encima no pesa ni 1MB.

Meter mods trae una fila de cambios en los sistemas que ya teníamos: el servidor ya no sólo debe validar la versión del cliente sino que este tenga además los debidos mods, en la versión esperada.
Hay que también crear los componentes más típicos de UI (botón, alerta, panel,..) de modo que desde lua puedan tirar de presets.
Y poco a poco cablear todos los sistemas a los que se quiere que puedan acceder: como leer los bloques que hay en determinadas coordinadas o spawnear bichos allí o realizar alguna acción a determinada hora del día.

Aunque claro, para muchas de estas funciones antes deberíamos de tener NPCs y ciclo de día/noche.

NPCs

Meterle IA a un juego es una matada, hacerlo en un multijugador lo es x2.
Lo primero que hay que considerar es cuál será el sistema de navegación que estos usarán. Unity tiene navmesh pero como todo lo que hace Unity, tiene sus problemas.

Imagina que quieres hacer que el usuario sea atacado por un grupo de enemigos. Unity no contempla esa posibilidad, lo que significa que los enemigos no se ven entre si y por tanto todos eligen la misma ruta (la más corta). Conformando una cola que no tiene el más mínimo sentido porque lo normal es que cada uno busque mantener la visión con su objetivo (para poder pegarle un tiro por ejemplo).

El apaño que suele hacerse es añadirle a cada enemigo un componente llamado NavMeshObstacle y que como puedes ver en una de las imágenes previas, lo que hace es quitar el espacio que ocupe del sistema de navegación (que es el área de color azul). De ese modo se marca el espacio como ocupado y el siguiente enemigo ni contempla la posibilidad de andar por ahí.
Pero claro, los elementos que tengan NavMeshObstacle NO pueden moverse. Así que lo que se hace es activar el componente, recalcular la ruta y desactivarlo constantemente.
Extraordinariamente asqueroso.

Otro detalle es que el cálculo de rutas de Unity es monothread, tiene que correr en el hilo principal.

Sabiendo que la solución oficial es una mierda pinchada en un palo he obtado por crear una que haga uso del grid generado al crear el mundo en bloques. Total, en el peor escenario será igual de mala que la oficial.

Añadiendo musiquita

Para crear algo de ambiente habría que ponerle algo de musiquita de fondo. El estilo más adecuado para este caso me ha parecido que era de 8-bit. Así que he cargado el juego de varias canciones que tienen licencia comercial.

Hacerlo también me ha obligado a dar otro gran paso: migrar al nuevo sistema de inputs de Unity.

Facilitando el remapeado de teclas

En Unity, si quieres saber si el jugador está pulsando determinada tecla, sólo tienes que hacer:

if (Input.GetKeyDown(KeyCode.Space)) {
  // está pulsando el Espaciador
}

Simple y cómodo, pero con un problema. La tecla está hardcodeada. El jugador no podrá cambiarla a otra.
El apaño que se hacía para solventarlo era meter una class de por medio que guardara la relación entre una acción y una tecla, de modo que el código quedara:

if (Input.GetKeyDown(GameInput.keyFor("Jump"))) {
  // está pulsando el Espaciador
}

Pues eso mismo hace el InputSystem de Unity pero de manera oficial y con más mejoras que también te permitan falsear las teclas que se pican. ¿Y por qué querría uno falsear las teclas que se pulsan? Para poder meter tests.

¿Estabilizando el juego?

Normalmente validar un flujo en una aplicación suele ser relativamente sencillo.
¿Quieres probar que el registro va automáticamente? Sólo tienes que seguir unos pasos:

  1. Ir a ejemplo.com/signup
  2. Rellenar el campo de email y de contraseña
  3. Pulsar el botón de enviar
  4. Revisar que en la base de datos esté el nuevo registro.

Cuando se trata de videojuegos sin embargo, la trama se complica. Pasamos a estar en un entorno 3D y si encima es un sandbox, hay mecánicas que pueden jugarte una mala pasada y hacer que una validación falle de manera intermitente.

  • ¿Y si cuando estás probando a poner un bloque encima de otro aparece un bicho por detrás y le da una hostia al jugador y lo desplaza antes de que ponga el bloque?
  • ¿Y si estás probando a darle un golpe a un árbol pero el juego tiene una mecánica de aleatoriedad que hace que falle?

Tienes que tratar de hacer que todo sea lo más determinístico posible. Todo random tiene que estar seedeado. Toda mecánica que pueda interferir tiene que estar controlada.
Aún así, suele ser la combinación de múltiples mecánicas la que provoca un bug.
Por ejemplo: Metí que al hacer clic derecho cuando no estuvieras sujetando nada hiciera zoom. Ahora cada vez que te bebías una poción el sistema te hacía zoom. Porque inicialmente la poción sí estaba, pero luego ya no.

No sé la forma perfecta de arreglar esto, pero he hecho he intentado que el juego tenga un mínimo de checks para evitar liadas en las mecánicas más básicas.
Lo suyo es que corrieran en cada PR, pero es algo que tengo que ver si se puede hacer porque sé que a Unity le gusta denunciar si su runtime se ejecuta de manera incorrecta.
Veremos, de momento tenemos tests hasta para los fluídos.

Haciendo fluir el agua

En su momento hice que los bloques pudieran tener físicas distintas, de modo que un bloquea de agua tuviera una gravedad distinta. Pero el agua no sólo trata de eso, también debería de poder fluir.
Igual que ocurre en Minecraft, pillar un bloque de agua y tirarlo al suelo provoca ahora su propagación en los bloques colindantes.
